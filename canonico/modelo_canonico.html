O modelo canônico em dois diagramas e um exemplo

Seis sistemas de origem, seis modalidades de arquivo, uma única tabela de destino — e uma operação que amarra tudo. Esta página mostra o percurso que todo dado faz, o que permite cruzar fontes tão diferentes, e como, a partir de qualquer número na camada final, se volta ao registro bruto que o gerou.

versão 3 · atualizado em 2026-09-11 · fonte: canonico/modelo_canonico.yaml

Por quê As duas teses que os diagramas servem

Toda decisão de modelagem aqui existe para sustentar uma destas duas afirmações. Se um detalhe do desenho não ajuda nenhuma delas, ele não deveria estar no desenho.

Heterogeneidade
A arquitetura ingere e integra dados de tipos muito diferentes — JSON, planilha, texto livre, imagem, áudio, PDF — sob um modelo canônico único. A coluna MODALIDADE_ORIGEM_COD em EVENTO permite contar quantas formas físicas de dado uma consulta atravessou; a coluna OPERACAO_COD é o que permite que essa consulta faça sentido — só se cruzam dados da mesma operação.
Linhagem
Dá para rastrear qualquer número da camada final até o registro bruto que o originou, incluindo qual modelo de IA fez a extração e com que versão de prompt. Em EVENTO, o primeiro elo é RECEPCAO_IDT (quando a fonte chegou como JSON) ou ARQUIVO_IDT (quando chegou como arquivo binário); o segundo, EXTRACAO_IDT, existe sempre que houve arquivo: registra como o conteúdo saiu dele — leitura direta ou IA — e, no segundo caso, qual modelo e qual prompt.

Diagrama 1 O processo: da fonte à camada Silver

O dado desce por camadas (o padrão Medallion): primeiro é guardado cru, depois catalogado sem ser interpretado, e só então convertido para o formato canônico. Cada camada tem um trabalho e só um.

  • Retângulo — uma tabela ou etapa
  • Hexágono — um processo (a transformação)
  • Cilindro — um armazenamento de arquivos
  • Seta cheia — o dado flui nesse sentido
  • Seta pontilhada — um ponteiro: a linha aponta para outra
  • Seta grossa — o fluxo principal

  1. Fontes

    Cada sistema entrega o que já produz, no formato em que produz. O C2_A manda JSON com a geometria embutida; o RELPER, uma planilha — ou o mesmo formulário impresso, assinado e escaneado; a artilharia, o Relatório de Bombardeio digitalizado; a seção de inteligência, um informe assinado; a rede de rádio, um arquivo de áudio. Nada é adaptado na origem.

  2. landing/

    O arquivo cai no armazenamento de objetos exatamente como chegou, byte a byte. Nenhum campo é lido ainda. Guardar antes de interpretar é o princípio de schema-on-read: pode-se ingerir uma fonte antes de modelá-la.

  3. Bronze — RECEPCAO_BRUTA, ARQUIVO e EXTRACAO

    Toda fonte passa por aqui antes da Silver. RECEPCAO_BRUTA guarda o registro estruturado de todo evento — o JSON nativo do C2, ou o sidecar, o pequeno .json de proveniência que acompanha cada arquivo (operação, unidade, data). ARQUIVO cataloga cada binário — onde está, seu hash, seu tipo, a operação da pasta — e nunca abre o binário. EXTRACAO grava uma linha por leitura de um binário, seja ela direta (célula de planilha, camada de texto do PDF) ou por IA (reconhecimento óptico, transcrição de fala, um modelo de linguagem local): qual ferramenta e versão, se houve inferência (INFERENCIA_INDIC, S/N), qual modelo e versão de prompt quando houve, quanto tempo levou. Todo binário passa por aqui — é o único caminho de ARQUIVO até EVENTO.

  4. De / para — modelo_canonico.yaml

    O job de transformação lê o YAML e, para cada campo de cada fonte, aplica a regra ali declarada. Não há if fonte == ... no código: integrar uma fonte nova é acrescentar um bloco no arquivo. É aqui que as tabelas de consulta entram — REF_UNIDADE traduz 1a Cia Fuz no código da unidade, REF_GAZETTEER troca BR-154 km 43 por uma coordenada, REF_ABREVIATURA resolve Fz para Fuzil.

  5. Silver — EVENTO e SITUACAO_UNIDADE

    Todas as fontes desembocam em EVENTO, uma tabela só, com o que toda fonte tem em comum: quem reportou, quando, onde, que tipo de fato, por qual sistema chegou, de que registro bruto veio. O que só o RELPER tem — efetivo, baixas, viaturas, dias de suprimento — vai para a extensão SITUACAO_UNIDADE, a única que existe.

Diagrama 2 A estrutura: quais tabelas apontam para quais

O mesmo modelo visto pelas chaves. As caixas listam só as colunas que importam para a leitura — PK marca a chave primária (identifica a linha), FK marca a chave estrangeira (aponta para a linha de outra tabela).

REF_GAZETTEER e REF_ABREVIATURA não aparecem como ligação porque não são chave estrangeira de nada: elas são consultadas durante a transformação, e o resultado já entra gravado em EVENTO e SITUACAO_UNIDADE. REF_UNIDADE aparece porque EVENTO.UNIDADE_REPORTANTE_COD guarda o código que ela define — e aponta para si mesma, porque toda unidade tem uma superior (menos a brigada, no topo). REF_OPERACAO aparece porque OPERACAO_COD é chave estrangeira de verdade em três tabelas: é o contexto que não se resolve e some, fica gravado.

O elo O que une tudo: a operação

Uma posição de GPS, um relatório de bombardeio, uma foto de incidente e uma mensagem de voz só podem ser cruzados se pertencem à mesma operação. É a chave de junção entre as fontes heterogêneas — e o recorte de toda visão da camada Gold: uma carta de situação é sempre de uma operação. Por isso EVENTO.OPERACAO_COD não é nulo: evento fora de operação não existe neste estudo.

A tabela REF_OPERACAO

Uma seed pequena e curada, no molde de REF_UNIDADE. O código é a chave natural da operação — nome + ano, escrita NOME_ANO. É a mesma chave que o C2_A usa por dentro: ele exporta "operacao": "Perseu" e "ano": "2024", formatados pelo próprio sistema, e não há dicionário a consultar — só juntar e pôr em maiúsculas.

OPERACAO_CODPERSEU_2024
OPERACAO_NOMEOperação Perseu
OPERACAO_TIPO_CODADESTRAMENTO
INICIO_DATA · FIM_DATA2026-05-04 … 2026-05-18
AREA_WKTPOLYGON((…))  (a área de operações)
UNIDADE_RESP_CODBDA51

A janela e a área servem de rede de segurança: um arquivo que chegou sem se identificar é atribuído à operação cuja INICIO/FIM e AREA_WKT contêm a hora e o ponto de captura (a transformação contexto_operacao).

O sidecar: uma forma só de dar contexto a qualquer arquivo

Um .xlsx, um PDF, uma foto, um .wav — nenhum se descreve bem: quem remeteu, quando, em que operação. A prática (arquivos de imagem de reconhecimento, gravadores de rádio, o padrão STANAG 4609) é não confiar no binário para se descrever. Aqui a regra vale para todo arquivo em landing/: ele chega acompanhado de um pequeno JSON de mesmo nome — o sidecar — com a proveniência.

landing/perseu_2024/relper/relper_bi511_matutino.xlsx     ← o binário    → ARQUIVO
landing/perseu_2024/relper/relper_bi511_matutino.json     ← o sidecar    → RECEPCAO_BRUTA

  relper_bi511_matutino.json
  {
    "operacao":     "PERSEU_2024",
    "om_remetente": "1o Btl Inf Mtz / 511",
    "data_hora":    "2024-11-27T06:00:00Z",
    "turno":        "MATUTINO"
  }

O sidecar entra em RECEPCAO_BRUTA exatamente como o JSON do C2_A; o binário entra em ARQUIVO; os dois se ligam por ARQUIVO_IDT. O que é sobre o arquivo (operação, unidade, data) vem do sidecar; o conteúdo — as células da planilha, as colunas do PDF — continua sendo lido do binário, por celula ou OCR.

Para o áudio o sidecar vem do voice logger: o gravador não transcreve, mas sempre carimba rede, frequência, hora e, num exercício, a operação. No C2_B, o registro JSON do incidente já é o sidecar da foto — não foi preciso inventar nada, só reconhecer o papel que ele cumpre.

Como a operação chega, por modalidade

FonteA operação vem de
JSON C2_Acampos nativos operacao + ano — a chave natural do sistema, formatada por ele
JSON C2_B relatocampo nativo no payload
C2_B incidente · RELPER · FOGOS · INTEL · VOZsidecar — o .json ao lado do arquivo
arquivo sem sidecar (fallback)hora + geo de captura dentro da janela e da área de REF_OPERACAO
O palpite e a referência. A operação é carimbada em ARQUIVO.OPERACAO_COD pela pasta de landing/ no momento da ingestão — é o que está sempre disponível. O valor de referência é o do sidecar ou do cabeçalho. Divergência entre os dois é sinal de qualidade, do mesmo tipo que a coordenada do EXIF contra a que o operador digitou.

De ponta a ponta Uma planilha e seu sidecar, do arquivo ao número rastreável

Um exemplo mínimo e concreto, para fixar o mecanismo. O 1º/511º BI Mtz remete o relatório periódico da manhã: um arquivo Excel com duas observações (uma linha por companhia) e duas colunas de medida (efetivo presente e viaturas operacionais), mais o sidecar. Segue-se tudo à medida que desce pelas camadas.

  1. O arquivo, como sai da unidade origem

    O 1º/511º BI Mtz remete dois arquivos: a planilha e o seu sidecar — o .json de proveniência, gerado pelo portal de submissão. Os cabeçalhos das colunas da planilha são fixados pelo estado-maior da brigada; as duas linhas de dados são o que varia.

    relper_bi511_2024-11-27_matutino.xlsx            (14,8 KB)

  Fração              | Ef Pres | Vtr Op
  --------------------|---------|-------
  1ª Cia Fuz/511      |   118   |   11
  2ª Cia Fuz/511      |   121   |   12

relper_bi511_2024-11-27_matutino.json           (o sidecar)

  { "operacao": "PERSEU_2024", "om_remetente": "1o Btl Inf Mtz / 511",
    "data_hora": "2024-11-27T06:00:00Z", "turno": "MATUTINO" }

    A planilha carrega o conteúdo (os números); o sidecar carrega o que é sobre o arquivo (operação, quem remeteu, quando).

  2. landing/ — os bytes, intactos object storage

    O par é copiado para o armazenamento de objetos exatamente como chegou. Nenhuma célula foi lida. Se a coluna Vtr Op nem existisse no formulário oficial, o arquivo entraria do mesmo jeito — o esquema só será exigido na leitura.

    s3a://lakehouse/landing/perseu_2024/relper/relper_bi511_2024-11-27_matutino.xlsx
s3a://lakehouse/landing/perseu_2024/relper/relper_bi511_2024-11-27_matutino.json

  3. ARQUIVO — o binário, uma linha bronze

    O manifesto do .xlsx. São duas observações dentro do arquivo, mas uma só linha aqui — a planilha é um documento único; o desdobramento em duas acontece na Silver.

    ARQUIVO_IDTarq_7b91f2
    OPERACAO_CODPERSEU_2024  (da pasta landing/perseu_2024/…)
    CONTEUDO_HASH_CODsha256:9f3c1a4e…
    ARQUIVO_URI_TXTs3a://…/perseu_2024/relper/relper_bi511_2024-11-27_matutino.xlsx
    MIME_TIPO_CODapplication/vnd.openxmlformats-officedocument.spreadsheetml.sheet
    MODALIDADE_CODPLANILHA
    RECEBIMENTO_DATA2024-11-27T09:12:07Z

  4. RECEPCAO_BRUTA — o sidecar, uma linha bronze

    O sidecar entra cru, inteiro, numa coluna de texto — sem um campo ser lido. É o mesmo tratamento que o JSON do C2_A recebe. Uma linha por arquivo remetido (que depois vira dois eventos).

    RECEPCAO_IDTrcp_c4d80a
    SISTEMA_ORIGEM_CODRELPER
    OPERACAO_CODPERSEU_2024  (do próprio sidecar — o valor de referência)
    MODALIDADE_CODPLANILHA
    CONTEUDO_JSON_TXT{"operacao":"PERSEU_2024","om_remetente":…}
    ARQUIVO_IDTarq_7b91f2  (liga o sidecar ao binário)
    O palpite e a referência. A operação aparece duas vezes: em ARQUIVO ela veio da pasta (landing/perseu_2024/…), carimbada na ingestão; em RECEPCAO_BRUTA ela veio do próprio sidecar. É esta segunda que EVENTO herda. As duas concordando é o esperado; divergirem seria sinal de arquivo na pasta errada — do mesmo tipo que a coordenada do EXIF contra a digitada.

  5. EXTRACAO — uma linha, sem IA bronze

    ARQUIVO e EXTRACAO são duas tabelas Bronze com papéis distintos, apesar do nome parecido: ARQUIVO diz que arquivo chegou — todo binário ganha uma linha, a planilha inclusive, e a ingestão nunca o abre; EXTRACAO diz o que foi lido de dentro dele, por quem e como. Todo binário passa pelas duas: ARQUIVO → EXTRACAO → EVENTO, um caminho só.

    Aqui a planilha é lida direto com uma biblioteca (openpyxl), célula por célula, resultado determinístico — mesma entrada, mesma saída. Isso gera uma linha em EXTRACAO com INFERENCIA_INDIC = N, FERRAMENTA_NOME = 'openpyxl 3.1.5', MODELO_NOME nulo (não há modelo) e as células em SAIDA_TXT. A versão da biblioteca fica registrada de propósito: bibliotecas têm defeitos, e sem ela um erro de leitura seria indistinguível de um erro no arquivo. O mesmo formulário impresso, assinado e escaneado chegaria como PDF e passaria por reconhecimento óptico: a linha teria INFERENCIA_INDIC = S, a ferramenta e o modelo do OCR. No YAML esse caminho é a receita situacao_digitalizada — um bloco de mapeamento, não uma tabela: escreve nas mesmas EVENTO e SITUACAO_UNIDADE que a planilha nativa. Uma pergunta de banca — quantos números passaram por IA? — vira uma condição: WHERE INFERENCIA_INDIC = 'S'.

  6. De/para — o job lê o modelo_canonico.yaml e monta o SQL transformação

    Para cada uma das duas linhas da planilha, as regras declaradas no YAML são aplicadas:

    do SIDECAR: operacao "PERSEU_2024" → referencia REF_OPERACAO → OPERACAO_COD = PERSEU_2024 data_hora "…T06:00:00Z" → ts_iso → OCORRENCIA_DATA = 2024-11-27 06:00:00 turno "MATUTINO" → dominio turno_relatorio → TURNO_COD = MATUTINO da PLANILHA (uma vez por linha): Fração "1ª Cia Fuz/511" → referencia REF_UNIDADE → UNIDADE_REPORTANTE_COD = BI511C1 Ef Pres "118" → celula → EF_PRESENTE_QNT = 118 (inteiro, não texto) Vtr Op "11" → celula → VTR_OPERACIONAL_QNT = 11 constantes / derivados: SISTEMA_ORIGEM_COD = RELPER MODALIDADE_ORIGEM_COD = PLANILHA TIPO_COD = SITUACAO_UNIDADE FUNCAO_COMBATE_COD = LOGISTICA FUNCAO_C2_INDIC = N REGISTRO_ORIGEM_COD = BI511-20260909-M-BI511C1 (sidecar: OM+data+turno; planilha: fração) ponteiros de linhagem: RECEPCAO_IDT = rcp_c4d80a ARQUIVO_IDT = arq_7b91f2
    Se a OM tivesse acrescentado uma coluna Obs que o formulário não previa, ela iria inteira para ATRIBUTO_EXTRA_TXT como {"Obs": "sem energia no gerador"} — preservada sem nunca ter sido modelada. Num banco relacional, essa coluna não teria onde entrar: seria descartada na carga ou exigiria alterar a tabela. É o argumento de schema-on-read em uma célula.

  7. EVENTO — duas linhas: o fan-out silver

    Um arquivo, duas companhias, dois eventos. O que toda fonte tem em comum.

    EVENTO_IDTOPERAÇÃOSISTEMAMODALIDADETIPOFUNÇÃOC2OCORRÊNCIAUNIDADERECEPCAO_IDTARQUIVO_IDT
    evt_3a0091PERSEU_2024RELPERPLANILHASITUACAO_UNIDADELOGISTICAN2024-11-27 06:00BI511C1rcp_c4d80aarq_7b91f2
    evt_3a0092PERSEU_2024RELPERPLANILHASITUACAO_UNIDADELOGISTICAN2024-11-27 06:00BI511C2rcp_c4d80aarq_7b91f2

    Os dois eventos herdam o mesmo RECEPCAO_IDT (o sidecar) e o mesmo ARQUIVO_IDT (a planilha) — um arquivo, um sidecar, dois eventos. Numa linha do C2_A, o ARQUIVO_IDT ficaria vazio (não há binário); num relato em texto do C2_B, idem.

  8. SITUACAO_UNIDADE — duas linhas, uma por evento silver

    Os números que só o relatório periódico tem. Ligada a EVENTO um-para-um pela chave EVENTO_IDT.

    EVENTO_IDTTURNOEF_PRESENTE_QNTVTR_OPERACIONAL_QNTATRIBUTO_EXTRA_TXT

    evt_3a0092MATUTINO12112—

  9. A volta: do número ao byte linhagem

    Pergunta de auditoria: de onde veio o 118 de efetivo presente da 1ª Cia?

    SITUACAO_UNIDADE.EF_PRESENTE_QNT = 118 (linha evt_3a0091) └─ EVENTO_IDT evt_3a0091 (OPERACAO_COD = PERSEU_2024) ├─ EVENTO.EXTRACAO_IDT = ext_5d20c7 │ └─ EXTRACAO: INFERENCIA_INDIC = N · FERRAMENTA_NOME = 'openpyxl 3.1.5' · MODELO_NOME nulo │ SAIDA_TXT → linha "1ª Cia Fuz/511", coluna "Ef Pres" = 118 ✔ │ └─ EXTRACAO.ARQUIVO_IDT = arq_7b91f2 │ └─ ARQUIVO.ARQUIVO_URI_TXT = s3a://…/perseu_2024/relper/…matutino.xlsx │ hash sha256:9f3c1a4e… (confere que o arquivo não mudou) ✔ └─ EVENTO.RECEPCAO_IDT = rcp_c4d80a └─ RECEPCAO_BRUTA.ORIGEM_URI_TXT = s3a://…/…matutino.json └─ o sidecar que disse "operacao: PERSEU_2024, remetente 1º/511º BI" ✔

    Dois ramos: o número saiu da planilha — e EXTRACAO diz com que biblioteca, em que versão, sem IA —, o contexto (operação, remetente) saiu do sidecar. Se fosse a versão escaneada, o mesmo ramo diria INFERENCIA_INDIC = S e com que ferramenta e modelo aquele 118 foi lido da imagem. É a tese de linhagem inteira num único número.

Referência As seis fontes

Cada linha da coluna “Bloco no YAML” é um conjunto de regras de/para dentro de fontes: — não uma tabela. Uma fonte pode ter mais de um bloco, um por forma de entrada: o RELPER chega como planilha ou como PDF assinado, e o C2_B, como texto ou como foto. Todos escrevem nas mesmas tabelas da coluna “Grava em”.

Fonte Modalidade Bloco no YAML Grava em Operação vem de Passa por IA?
C2_A JSON posicao, mcc RECEPCAO_BRUTA → EVENTO nome + ano no payload Não — geometria já vem nativa
C2_B TEXTO relato RECEPCAO_BRUTA → EVENTO campo no payload LLM: tipo, função de combate, prioridade, confiabilidade, credibilidade
C2_B IMAGEM incidente RECEPCAO_BRUTA (sidecar) + ARQUIVO → EVENTO sidecar (o registro do incidente) Não — a coordenada vem do metadado da foto
RELPER PLANILHA situacao RECEPCAO_BRUTA (sidecar) + ARQUIVO → EVENTO + SITUACAO_UNIDADE sidecar Não — leitura direta de célula (EXTRACAO com INFERENCIA_INDIC = N)
RELPER PDF situacao_digitalizada RECEPCAO_BRUTA (sidecar) + ARQUIVO → EVENTO + SITUACAO_UNIDADE sidecar OCR + LLM: unidade reportante
FOGOS PDF relatorio_bombardeio RECEPCAO_BRUTA (sidecar) + ARQUIVO → EVENTO sidecar OCR + LLM: data, prioridade. Só a 1ª parte do Anexo I (informes de observador sobre bombardeio inimigo) vira evento
INTEL PDF informe RECEPCAO_BRUTA (sidecar) + ARQUIVO → EVENTO sidecar OCR + LLM: data, tipo, prioridade. A avaliação B2 é lida do cabeçalho, não inferida
VOZ AUDIO transcricao RECEPCAO_BRUTA (sidecar) + ARQUIVO → EVENTO sidecar do voice logger Transcrição de fala + LLM: prioridade, função. A hora vem do gravador
Todo binário gera pelo menos uma linha em EXTRACAO; nas linhas marcadas com IA ela traz INFERENCIA_INDIC = S, modelo e prompt — é o que torna a extração auditável.

Referência Vocabulário das transformações

O nome que aparece em transformacao: no de/para. O código de cada uma vive no job de transformação, não no YAML — o YAML só diz qual aplicar a cada campo.

direto
Copia o valor sem mexer.
json
Extrai um campo do payload JSON pelo caminho indicado. O payload fica preservado inteiro em RECEPCAO_BRUTA; a leitura acontece aqui.
celula
Lê uma célula da planilha pelo cabeçalho decretado no formulário.
ts_iso / ts_br
Texto vira data — no formato ISO ou no formato brasileiro.
ponto_de_latlon
Par de números vira ponto geográfico.
geojson_para_wkt
Geometria em GeoJSON vira o mesmo em WKT (o texto padrão do modelo).
dms_para_ponto
Coordenada em grau-minuto-segundo, escrita por extenso, vira ponto.
decametrica_para_ponto
Coordenada métrica militar (ex.: 03250-10550) vira ponto.
gazetteer
Nome de lugar vira ponto, consultando REF_GAZETTEER. Não converte — consulta.
abreviatura
Abreviatura digitada vira termo, consultando REF_ABREVIATURA.
dominio
Valor da origem vira valor canônico, pelos sinônimos da lista fechada.
referencia
Valor da origem vira o código de uma tabela de consulta.
contexto_operacao
Hora e ponto de captura viram OPERACAO_COD, pela janela e pela área de REF_OPERACAO. É o recurso para o arquivo que chegou sem se identificar.
constante
Grava um valor fixo, igual para toda linha daquela fonte.
derivado
Calculado por uma regra declarada no próprio campo de destino.
split_escala
Um campo de origem, dois de destino: B2 vira confiabilidade B e credibilidade 2.
sobra
Tudo que o formulário não previa vai para uma coluna JSON, com o nome que a unidade deu.
