## 6. Configuração da Linhagem (Lineage)

A linhagem de dados no OpenMetadata mapeia o fluxo completo Bronze → Silver → Gold, com 10 arestas cobrindo 8 tabelas Iceberg.

### 6.1 Problema descoberto: Spark OpenLineage não gera edges no OM

O Spark OpenLineage listener (`io.openlineage.spark.agent.OpenLineageSparkListener`) versão 1.18.0 com Iceberg apresenta três limitações fundamentais que **impedem** a geração automática de edges de linhagem no OpenMetadata:

| Limitação | Detalhe |
| --- | --- |
| Namespace | Eventos emitidos com `namespace=default` em vez do namespace esperado pelo OM |
| Formato dos datasets | Datasets identificados como paths S3 (`namespace=s3://lakehouse`, `name=warehouse/silver.db/gps`) em vez de `catalog.schema.table` |
| Inputs vazios no COMPLETE | Eventos `COMPLETE` do Spark Iceberg handler emitem `inputs: []` vazio — sem inputs, o OM não consegue inferir arestas |

**Diagnóstico:** interceptamos os eventos reais do Spark via HTTP logger e confirmamos que os payloads chegam ao OM (status 200), mas a resposta sempre contém `"lineageEdgesCreated": 0` e a mensagem `"Event processed, no lineage edges created"`.

> O listener Spark OpenLineage continua ativo nos DAGs — ele envia metadados úteis de execução (duração, facets Spark) ao OM, mas **não gera edges de linhagem**. As edges são criadas pelo mecanismo abaixo.

### 6.2 Solução implementada: `lineage_callback` centralizado

Em vez de injeção manual por script ou task dedicada, a linhagem agora é emitida **automaticamente** a cada execução bem-sucedida de qualquer task Spark, via `on_success_callback` do Airflow.

| Componente | Arquivo | Função |
| --- | --- | --- |
| Mapa de linhagem | `airflow/dags/helpers/lineage_emitter.py` | `LINEAGE_MAP` — dict com todas as relações `task_id → (inputs, outputs)` |
| Callback genérico | `airflow/dags/helpers/lineage_emitter.py` | `lineage_callback` — consulta `LINEAGE_MAP` pelo `task_id` e emite evento `COMPLETE` |
| Emitter HTTP | `airflow/dags/helpers/lineage_emitter.py` | `emit_lineage` → `POST /api/v1/openlineage/lineage` no OM |

**Como funciona:**

1. Todo DAG inclui `"on_success_callback": lineage_callback` no `default_args`
2. Quando um task Spark finaliza com sucesso, o Airflow chama `lineage_callback(context)`
3. O callback consulta `LINEAGE_MAP[task_id]` para obter `(inputs, outputs)`
4. Emite um evento OpenLineage `COMPLETE` com os datasets em formato `catalog.schema.table` via `POST` ao endpoint nativo do OM
5. O OM processa o evento e cria as edges de linhagem

**Para registrar linhagem de um novo task:** basta adicionar uma entrada no `LINEAGE_MAP`:

```python
# Em airflow/dags/helpers/lineage_emitter.py
LINEAGE_MAP["novo_task_id"] = (
    ["lakehouse.silver.tabela_input"],
    ["lakehouse.gold.tabela_output"],
)
```

### 6.3 Grafo de linhagem

```
bronze.dados ──┬──→ silver.gps    ──┬──→ gold.posicionamento_atual
               │                    ├──→ gold.latencia_por_batalhao ←──┐
               │                    └──→ gold.cobertura_temporal       │
               ├──→ silver.sitrep ──┬──→ gold.sitrep_consolidado      │
               │                    └──→ gold.latencia_por_batalhao ───┘
               └──→ silver.sensor ──┬──→ gold.atividade_sensores
                                    └──→ gold.latencia_por_batalhao
```

Total: **10 arestas**, 8 tabelas, todas com `source=OpenLineage` no OM.

### 6.4 Variável de ambiente obrigatória

O emitter requer um JWT do bot de ingestão do OM:

| Variável | Onde obter | Onde configurar |
| --- | --- | --- |
| `OM_INGESTION_BOT_JWT` | OM → Settings → Bots → `ingestion-bot` → copiar token | `.env` ou Secret do Kubernetes |

Sem esse token, o callback exibe `WARNING: OM_INGESTION_BOT_JWT não definido` e **não bloqueia** a execução do task.

### 6.5 Verificar a linhagem

1. Acesse <http://localhost:8585>
2. Navegue até qualquer tabela Silver ou Gold (ex: **Explore** → **Tables** → `silver.sensor`)
3. Clique na aba **Lineage**
4. O grafo deve mostrar as conexões upstream e downstream
5. Cada edge deve exibir `source: OpenLineage` nos detalhes

### 6.6 Nota sobre o Spark OpenLineage listener

O listener Spark (`spark.extraListeners=io.openlineage.spark.agent.OpenLineageSparkListener`) permanece ativo nos DAGs e no `openlineage.yml`. Ele envia eventos START/RUNNING/COMPLETE ao OM com facets de execução (duração, métricas Spark, versão), mas é o `lineage_callback` que efetivamente cria as arestas de linhagem. Se no futuro o handler Iceberg do OpenLineage for corrigido para emitir datasets em formato catalog e incluir inputs no COMPLETE, a migração para linhagem 100% automática será possível removendo o callback e ajustando o `openlineage.yml`.

## 8. Guia de implantação para a equipe GitLab/Kubernetes

> Esta seção destina-se à equipe de infraestrutura responsável por migrar o projeto do ambiente local (Docker Compose) para o cluster corporativo (GitLab CI/CD + Kubernetes).

### 8.1 Repositório e CI/CD (GitLab)

- **Importe o repositório** diretamente do diretório atual — já está em git (`git remote add origin <url-do-gitlab>`).
- Crie um arquivo `.gitlab-ci.yml` na raiz com ao menos três stages: `build` (build das imagens Spark e Airflow), `test` (smoke test nos containers) e `deploy` (apply dos manifests Kubernetes).
- As imagens customizadas são apenas **duas**: `infra/spark/Dockerfile` e `infra/airflow/Dockerfile`. As demais (`postgres`, `minio`, `trino`, `openmetadata`) usam imagens públicas — não precisam de build.
- Publique as imagens buildadas no **GitLab Container Registry** e atualize os manifests Kubernetes para referenciar esse registry.
- O arquivo `.env` **nunca deve ser commitado**. Use **GitLab CI/CD Variables** (Settings → CI/CD → Variables) para armazenar todos os valores sensíveis e injete-os como `envFrom: secretRef` nos Pods.

### 8.2 Secrets e ConfigMaps (Kubernetes)

Crie um `Secret` com as variáveis sensíveis e um `ConfigMap` com as não-sensíveis:

```yaml
# secret-dlh.yaml — nunca versionar com valores reais; gere via CI
apiVersion: v1
kind: Secret
metadata:
  name: dlh-secrets
  namespace: dlh
stringData:
  POSTGRES_USER: dlh_admin
  POSTGRES_PASSWORD: dlh_pass_2026
  MINIO_ROOT_USER: minio_admin
  MINIO_ROOT_PASSWORD: minio_pass_2026
  AIRFLOW__CORE__FERNET_KEY: 46BKJoQYlPPOexq0OhDZnIlNepKFf87WFwLt0nIe3aY=
  AIRFLOW__WEBSERVER__SECRET_KEY: dlh_airflow_secret_2026
  OM_INGESTION_BOT_JWT: "<token do bot ingestion-bot do OM>"
```

> **`OM_INGESTION_BOT_JWT`** é necessário para que o `lineage_callback` emita eventos OpenLineage ao OM. Obtenha em OM → Settings → Bots → `ingestion-bot` → copiar token. Injete nos Pods do Airflow (scheduler e webserver) via `envFrom: secretRef`.

> **Dica de produção:** gere novas chaves Fernet com `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. As chaves do `.env` local são apenas para desenvolvimento.

### 8.3 Ordem de dependência dos serviços

Respeite a seguinte ordem de startup ao criar os manifests ou Helm charts:

1. **postgres** + **minio** (stateful — use `StatefulSet` com `PersistentVolumeClaim`)
2. **minio-init** (`Job` de inicialização — cria os buckets `landing` e `lakehouse`)
3. **hive-metastore** (depende de postgres saudável e minio-init concluído)
4. **spark-master** + **spark-worker** (depende de hive-metastore)
5. **trino** + **airflow-init** (depende de hive-metastore)
6. **airflow-webserver** + **airflow-scheduler** (depende de airflow-init)
7. **elasticsearch** (independente, mas precisa estar healthy antes do OM)
8. **execute-migrate-all** (`Job` — depende de postgres e elasticsearch healthy)
9. **openmetadata** (depende de execute-migrate-all concluído com sucesso)
10. **openmetadata-ingestion** (depende de openmetadata)

Use `initContainers` com `wget -q --spider <healthcheck-url>` para garantir a ordem no Kubernetes.

### 8.7 Linhagem automática no Kubernetes

O mecanismo de linhagem (`lineage_callback`) funciona automaticamente nos DAGs e não requer configuração adicional além de:

1. **Incluir `airflow/dags/helpers/`** na imagem do Airflow ou como volume montado no pod do scheduler/webserver — o diretório contém `__init__.py` e `lineage_emitter.py`
2. **Definir `OM_INGESTION_BOT_JWT`** como variável de ambiente nos pods Airflow (seção 8.2)
3. **Definir `OPENMETADATA_URL`** se o hostname do OM for diferente de `http://openmetadata:8585` (ajustar para o Service DNS do cluster, ex: `http://openmetadata.dlh.svc.cluster.local:8585`)

**Sobre o Spark OpenLineage listener:**
- O listener (`spark.extraListeners`) continua ativo e envia eventos ao OM, mas **não gera edges de linhagem** devido a limitações do handler Iceberg no OpenLineage 1.18.0 (seção 6.1)
- O arquivo `infra/openlineage/openlineage.yml` é montado no container do Airflow como bind mount — no Kubernetes, monte-o como `ConfigMap`
- O `lineage_callback` é o mecanismo que efetivamente cria as edges — basta que o Airflow consiga alcançar o OM via HTTP

**Manutenção:** ao criar novos tasks Spark, adicione a relação input/output no `LINEAGE_MAP` em `lineage_emitter.py`. Não há script externo para executar nem task dedicada — tudo é automático via `on_success_callback`.

- [ ] `kubectl get pods -n dlh` — todos os pods em `Running` ou `Completed`
